1. What you are building

Each GPU model (PDAC, HoVer-Net, EC, DeepLIIF, …) lives in its own private GitHub repo. That repo does not contain the shared worker runtime. It only contains:

  • model code (models/, optional module/)
  • requirements.txt
  • a thin Dockerfile that starts FROM a shared base image
  • azure-pipelines.yml

The shared runtime (queue client, health endpoints, overlay writer, Redis glue) is published once from AIMLab-UBC/aim-inference-platform as: 

aimlabacr.azurecr.io/aimlab/aim-inference-worker-base:main

A push to a model repo’s main should do this automatically:

Developer │ git push origin main ▼ GitHub (AIMLab-UBC/aim-inference-worker-<name>) │ webhook (installed by Azure DevOps) ▼ Azure DevOps pipeline worker-<name> │ runs on self-hosted agent pool k3s-host (this VM) │ docker build FROM worker-base:main ▼ Azure Container Registry aimlabacr │ tags: :<12-char-sha> and :main ▼ k3s Deployment worker-<name> │ imagePullPolicy: Always + secret acr-pull │ next KEDA scale-up (or rollout restart) pulls new :main ▼ Pod runs inference from Redis stream inference:tasks:<model>
Do not enable PR triggers on these pipelines. They push the mutable :main tag that production pods pull. A PR build would overwrite the live image with unmerged code. Leave pr: none in YAML.

3. One-time platform prerequisites

These were done once when CI was first stood up. Skip them when adding a model unless you are building a new environment from scratch.

3.1 Azure: resource group + ACR

# Already done on this subscription ("Azure credit")
az group create -n rg-aim-inference -l eastus2
az acr create -n aimlabacr -g rg-aim-inference --sku Basic
# Resulting login server: aimlabacr.azurecr.io

An AcrPush service principal and a read-only pull token (k3s-pull) were created and saved under ~/.config/aimlabacr-* on this host only. The pull credentials feed the Kubernetes secret acr-pull.

3.2 Azure DevOps project + PAT

  1. Org: https://dev.azure.com/aimlabdev
  2. Project: cpathportal
  3. Create a Personal Access Token with at least: Agent Pools (Read & manage), Build (Read & execute), Code (Read), Service Connections (Read, query & manage).
export AZURE_DEVOPS_EXT_PAT='…'
export ADO_ORG=https://dev.azure.com/aimlabdev
az devops configure --defaults organization="$ADO_ORG" project=cpathportal

3.3 Self-hosted agent pool k3s-host

Builds need the host’s Docker daemon, NVIDIA runtime, and local disk — so they run on this VM, not Microsoft-hosted agents.

  1. Create agent pool k3s-host in Project settings → Agent pools.
  2. Install the agent under /home/ubuntu/azdo-agent (deploy/azure-devops/install-agent.sh).
  3. The agent process must be in the docker group, or every push fails with permission denied on /var/run/docker.sock.
Reboot caveat. The agent was started by hand with sg docker -c './bin/Agent.Listener run --startuptype service'. It is not yet a durable systemd unit. After a reboot, start it again (or finish ./svc.sh install).

3.4 Service connections

GitHub · github-aimlab-ubc

Project settings → Service connections → New → GitHub (OAuth or GitHub App). Grant access to every AIMLab-UBC/aim-inference-worker-* repo and extract_areas. The account needs admin on those repos so Azure DevOps can create webhooks.

Azure Resource Manager · aim-inference-acr

Points at the subscription that owns ACR. Used by the AzureCLI@2 task. Enable it for all pipelines (or authorize each pipeline on first run).

3.5 Shared base image pipeline

Pipeline worker-base (id 1) builds from AIMLab-UBC/aim-inference-platform / azure-pipelines.yml on branches main, but only when platform / Docker paths change. It pushes aim-inference-worker-base:<sha> and :main.

Model repos depend on that :main tag. If you change the shared runtime, rebuild the base, then rebuild each model (queue their pipelines or push a no-op commit).

4. How the current system was set up

This is the historical path that produced today’s four model pipelines.

1

Split models out of the monorepo

scripts/seed_model_repos.sh created local checkouts with a thin Dockerfile, requirements, model code, README, and azure-pipelines.yml. scripts/push_model_repos.sh created private GitHub repos and pushed main (token used only on the push URL, never stored in .git/config).

2

Publish worker-base

Added a worker-base stage to docker/Dockerfile, trimmed azure-pipelines.yml so platform CI builds only the base (not the four models), and fixed CI to set TARGETS=worker-base and skip SSH-only submodules.

3

Register one Azure Pipeline per GitHub repo

Pipelines 3–6 were created against GitHub via service connection github-aimlab-ubc, pool k3s-host, YAML path azure-pipelines.yml. Early attempts that pointed at Azure DevOps mirror repos failed checkout auth — they were re-pointed to GitHub.

4

Fix the first green builds

Order matters: set a private DOCKER_CONFIG before az acr login, then build/tag/push. Grant the agent Docker socket access. Keep pr: none.

5

Point k3s workers at ACR :main

Overlay deploy/k8s/overlays/k3s-local rewrites image names to aimlabacr.azurecr.io/aimlab/…:main, adds imagePullSecrets: acr-pull, sets imagePullPolicy: Always, and keeps KEDA max replicas at 4 (one per T4).

6

Restore missing GitHub webhooks

Because some pipelines were re-pointed with an API PATCH, GitHub had no webhooks. Saving a YAML CI trigger on each definition made Azure DevOps install the push hook. Without that step, commits never queue a build.

5. Do this yourself for another repo (manual)

Replace <name> everywhere with a short slug matching the gateway model id (letters, digits, underscores). Example: tumor_grader → repo aim-inference-worker-tumor-grader, pipeline worker-tumor-grader, image aim-inference-worker-tumor-grader.

Step A — Create the GitHub repository

  1. Open aim-inference-worker-template.
  2. Use Use this template → Create a new repository.
  3. Owner: AIMLab-UBC. Name: aim-inference-worker-<name>. Private.
  4. Or clone the template locally and push: 
    gh repo create AIMLab-UBC/aim-inference-worker-<name> \
  --private --template AIMLab-UBC/aim-inference-worker-template
  5. In GitHub → the Azure Pipelines / OAuth app used by github-aimlab-ubc → grant this new repo. Admin access is required for webhooks.

Step B — Fill in the model contents

Minimum layout (matches the working PDAC repo):

aim-inference-worker-<name>/
├── azure-pipelines.yml
├── Dockerfile
├── README.md
├── requirements.txt
├── models/
│   └── <name>_model.py      # BaseAIModel implementation
└── module/                  # optional native / vendor code

Dockerfile (copy and edit)

ARG BASE_IMAGE=aimlabacr.azurecr.io/aimlab/aim-inference-worker-base:main
FROM ${BASE_IMAGE}
USER root
COPY requirements.txt /tmp/model.txt
RUN pip install -r /tmp/model.txt
COPY models/ /app/models/
COPY module/ /app/module/
USER 10001
ENV MODEL_NAME=<name> HF_HOME=/tmp/hf
Weights stay on the host. Put checkpoints under /data/models on the k3s node (already mounted read-only into workers). Do not commit multi-gigabyte weights into GitHub.

azure-pipelines.yml (copy and edit)

# Build this model worker FROM the shared base image and push to ACR.
trigger:
  batch: true
  branches:
    include:
      - main
pr: none

variables:
  ACR_NAME: aimlabacr
  REGISTRY: aimlabacr.azurecr.io/aimlab
  IMAGE_NAME: aim-inference-worker-<name>
  azureSubscription: aim-inference-acr
  BASE_IMAGE: aimlabacr.azurecr.io/aimlab/aim-inference-worker-base:main

pool:
  name: k3s-host

steps:
  - checkout: self
    submodules: recursive   # set false if you have no submodules
    fetchDepth: 1

  - task: AzureCLI@2
    displayName: az acr login + docker build/push
    inputs:
      azureSubscription: $(azureSubscription)
      scriptType: bash
      scriptLocation: inlineScript
      inlineScript: |
        set -euo pipefail
        SHORT_SHA="$(echo '$(Build.SourceVersion)' | cut -c1-12)"
        # CRITICAL: DOCKER_CONFIG before az acr login
        DOCKER_CONFIG="${AGENT_TEMPDIRECTORY}/docker-config"
        mkdir -p "$DOCKER_CONFIG"
        export DOCKER_CONFIG
        az acr login --name "$(ACR_NAME)"
        IMAGE="$(REGISTRY)/$(IMAGE_NAME):${SHORT_SHA}"
        MAIN="$(REGISTRY)/$(IMAGE_NAME):main"
        docker build -t "$IMAGE" --build-arg BASE_IMAGE="$(BASE_IMAGE)" .
        docker tag "$IMAGE" "$MAIN"
        docker push "$IMAGE"
        docker push "$MAIN"
        echo "Pushed $IMAGE and $MAIN"
If DOCKER_CONFIG is set after az acr login, the push fails with “authentication required”. The login writes credentials into whatever DOCKER_CONFIG is at that moment; Docker later reads a different empty config. Always mkdir + export first.

Commit and push:

git add -A
git commit -m "Initial <name> worker from template"
git push -u origin main

Step C — Create the Azure Pipeline (UI — preferred)

Creating the pipeline from the browser against the GitHub repo is the reliable way to get the webhook installed automatically.

  1. Open Pipelines → New pipeline.
  2. Where is your code? → GitHub.
  3. Pick connection github-aimlab-ubc (or authorize again if prompted).
  4. Select AIMLab-UBC/aim-inference-worker-<name>.
  5. Configure → Existing Azure Pipelines YAML file → path /azure-pipelines.yml, branch main.
  6. Rename the pipeline to worker-<name> (⋯ → Rename / pipeline settings).
  7. Confirm the default agent pool is k3s-host (the YAML pool: block should already set this).
  8. Run once. On first run, Azure DevOps may ask you to Permit the aim-inference-acr service connection — click Permit / Authorize.

Step C′ — Create the pipeline (CLI — optional)

az pipelines create \
  --org https://dev.azure.com/aimlabdev \
  --project cpathportal \
  --name worker-<name> \
  --repository AIMLab-UBC/aim-inference-worker-<name> \
  --repository-type github \
  --branch main \
  --yml-path azure-pipelines.yml \
  --skip-first-run false \
  --service-connection github-aimlab-ubc \
  -o table
If the CLI says Could not create service hooks subscription. The repository does not reference a service connection. use the UI path above, or follow §6 to force the webhook after creation.

Step D — Confirm the webhook exists

  1. GitHub → aim-inference-worker-<name> → Settings → Webhooks.
  2. You must see a hook whose Payload URL starts with https://dev.azure.com/aimlabdev/_apis/public/hooks/externalEvents.
  3. Events: Pushes (CI). No Pull requests needed.
  4. If the list is empty, the pipeline will only run when you click Queue — go to §6.

6. Webhooks and CI triggers (the common failure)

Azure DevOps installs the GitHub webhook when a pipeline is created from GitHub or when a YAML CI trigger is saved on a GitHub-backed definition. A raw REST PATCH that only changes repository.url does not create the hook — that is why the aim-inference-worker-* repos had empty Webhooks pages until they were repaired.

Repair from the Azure DevOps UI

  1. Pipelines → worker-<name> → Edit.
  2. Open the Triggers menu (⋯ or the Triggers tab).
  3. Ensure Override the YAML continuous integration trigger is off (so the YAML trigger: block is used).
  4. Save. Saving often (re)installs the GitHub webhook.
  5. Refresh GitHub → Settings → Webhooks and confirm the hook appeared.

Repair from the API (what we used)

PUT the build definition with a YAML-sourced CI trigger (settingsSourceType: 2) and repository.properties.manageWebhook: "true". That made Azure DevOps create one push webhook per repo. 

# Example sketch — replace DEFINITION_ID and REPO
# 1) GET definition → /tmp/def.json
# 2) set triggers to YAML CI + manageWebhook true
# 3) PUT definition back

az devops invoke \
  --org https://dev.azure.com/aimlabdev \
  --area build --resource definitions \
  --route-parameters project=cpathportal definitionId=DEFINITION_ID \
  --http-method GET --api-version 7.1 -o json > /tmp/def.json

# edit /tmp/def.json then:
az devops invoke \
  --org https://dev.azure.com/aimlabdev \
  --area build --resource definitions \
  --route-parameters project=cpathportal definitionId=DEFINITION_ID \
  --query-parameters definitionId=DEFINITION_ID \
  --http-method PUT --api-version 7.1 \
  --in-file /tmp/def-put.json -o json

Confirm Azure DevOps sees the hook:

EP=85897963-fd50-40ca-8838-e25a362675c5   # id of github-aimlab-ubc
az devops invoke --org https://dev.azure.com/aimlabdev \
  --area build --resource webhooks \
  --route-parameters project=cpathportal providerName=github \
  --query-parameters serviceEndpointId=$EP \
    repository=AIMLab-UBC/aim-inference-worker-<name> \
  --http-method GET --api-version 7.1 -o json

Expected: count: 1 and a url under dev.azure.com/.../externalEvents.

7. Wire the new image into k3s / Argo CD

A green pipeline only publishes an image. The cluster still needs a Deployment, a KEDA ScaledObject, and overlay image tags.

7.1 Scaffold platform manifests

cd ~/code/extract_areas
python scripts/new_model.py <name> --min 0
# or: make new-model

This adds roughly:

  • deploy/k8s/base/workers/worker-<name>.yaml — Deployment + ScaledObject on stream inference:tasks:<name>
  • an entry in deploy/k8s/base/kustomization.yaml
  • a local Dockerfile stage (optional; CI still builds from the model repo)

7.2 Edit the k3s-local overlay

In deploy/k8s/overlays/k3s-local/kustomization.yaml:

  1. Add under images:: 
    - name: aimlab/aim-inference-worker-<name>
  newName: aimlabacr.azurecr.io/aimlab/aim-inference-worker-<name>
  newTag: main
  2. Include the model label in the patch that adds imagePullSecrets: acr-pull and imagePullPolicy: Always (selector today: aim.inference/model in (pdac, hovernet, ec_cancer, deepliif, …)).

7.3 Image Updater annotations (optional today)

In deploy/k8s/argocd/application.yaml, extend argocd-image-updater.argoproj.io/image-list. Note: Image Updater v0.17.0 currently skips this app on Argo CD 3.x (status.sourceType empty). Pods still get new builds because of imagePullPolicy: Always on :main.

7.4 Weights + secrets

  • Copy model weights to /data/models/… on this host.
  • If the model needs Hugging Face downloads, ensure HF_TOKEN is in inference-secrets (re-run overlays/k3s-local/create-secret.sh from deploy/compose.env — never commit that file).

7.5 Push platform branch and sync

git add deploy/k8s scripts docker   # whatever new_model.py touched
git commit -m "Add worker-<name> Deployment and ACR image wiring"

8. Verify end to end

  1. Webhook delivery — push a tiny README tweak to the model repo. 
    git commit --allow-empty -m "ci: ping"
git push origin main
    GitHub → Webhooks → Recent Deliveries → expect HTTP 200.
  2. Pipeline — ADO builds should show a new run of worker-<name> without you clicking Queue. Green = image in ACR.
  3. ACR tags 
    az acr repository show-tags -n aimlabacr \
  --repository aimlab/aim-inference-worker-<name> -o table
    You should see main and a 12-character sha.
  4. Cluster 
    kubectl -n aim-inference get deploy,scaledobject | grep <name>
kubectl -n aim-inference get deploy worker-<name> \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}{.spec.template.spec.containers[0].imagePullPolicy}{"\n"}'
    Expect …/aim-inference-worker-<name>:main and Always.
  5. Force a pull of the new build (if a pod was already running): 
    kubectl -n aim-inference rollout restart deploy/worker-<name>
  6. Gateway catalogue 
    curl -s -H "Authorization: Bearer $GATEWAY_API_TOKEN" \
  http://127.0.0.1:30080/v1/models | jq
  7. Portal — grant the model to the user group in Access grants, then start a single-slide or Batch AI job and watch KEDA scale the worker from 0 → 1.

9. Day-2 operations

ChangeWhat to do

Shared worker runtime Push extract_areas → worker-base pipeline → then rebuild every model pipeline.
CPU / env / scaling Edit manifests under deploy/k8s/, push main, Sync Argo CD.
Roll back a bad model build List ACR tags; set newTag: <old-sha> in the overlay; push + sync.

10. Troubleshooting

SymptomLikely causeFix
Push to GitHub, no pipeline run No webhook, or UI override disabled YAML triggers §6 — confirm hook on GitHub; turn off “Override YAML CI trigger”; save
fatal: Authentication failed for dev.azure.com/.../_git/… Pipeline still points at an ADO mirror repo Edit pipeline → Get sources → GitHub repo via github-aimlab-ubc
permission denied on docker.sock Agent not in docker group sg docker -c './bin/Agent.Listener …' or fix the systemd unit
ACR push: authentication required DOCKER_CONFIG set after az acr login Reorder YAML: mkdir/export DOCKER_CONFIG, then login, then push
Build asks for empty submodule / SSH to GitHub submodules: recursive but submodule is SSH-only or empty Use submodules: false, or fix submodule URLs to HTTPS with a token
Pipeline green, cluster still runs old code Cached :main with IfNotPresent, or no restart Ensure overlay sets imagePullPolicy: Always; rollout restart
Pod ImagePullBackOff Missing acr-pull secret or wrong image name Re-run create-acr-pull-secret.sh; check overlay images: block
Webhook 200 but no build Branch filter (only main) or path filters Push to main; for worker-base also touch a watched path
